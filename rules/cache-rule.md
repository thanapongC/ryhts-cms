# Cache System Rules

This project currently runs in **real-time CMS mode**. Frontend pages should reflect Strapi changes immediately, so the previous SSR/CDN cache design is disabled.

## 1. Current Architecture

The active request path is:

```text
Browser
  |
Astro frontend with no-store response headers
  |
Strapi API fetches with cache: "no-store"
  |
Strapi CMS source of truth
```

There is no active SSR in-memory cache and no frontend cache invalidation lifecycle to maintain.

## 2. Frontend Response Headers

Location:

- `web/src/middleware.ts`

All frontend page responses should send no-cache headers:

```http
Cache-Control: no-store, no-cache, must-revalidate, max-age=0, s-maxage=0
Pragma: no-cache
Expires: 0
```

Rules:

- Do not add `s-maxage`, `stale-while-revalidate`, or route-specific TTLs while real-time CMS mode is active.
- API and generated metadata routes that expose dynamic CMS state should also send no-store headers.
- Static fingerprinted assets generated by Astro can still be cached by the asset pipeline or web server.

Current no-store routes include:

- Standard page responses through `web/src/middleware.ts`
- `web/src/pages/api/og.ts`
- `web/src/pages/robots.txt.ts`
- `web/src/pages/sitemap.xml.ts`

## 3. Strapi Fetch Rules

Location:

- `web/src/lib/strapi.ts`

Every frontend Strapi fetch must use:

```ts
cache: "no-store"
```

Rules:

- Do not wrap Strapi fetches with an in-memory cache.
- Do not rely on browser or CDN cache for CMS visibility flags such as `isPageEnabled` or `isActive`.
- Keep fetch error handling so static fallback content can render when Strapi is unavailable.
- When Strapi is online and returns disabled or inactive content, respect that CMS state instead of falling back to static content.

## 4. Compatibility Cache Module

Location:

- `web/src/lib/cache.ts`

This file is retained only as a compatibility module for existing imports. Its cache functions are no-ops.

Rules:

- Do not use `cacheGet`, `cacheSet`, or `cacheInvalidate` for new behavior while real-time CMS mode is active.
- If caching is reintroduced later, update this rule file, `web/src/lib/cache.ts`, `web/src/middleware.ts`, Strapi lifecycle behavior, and verification commands in the same change.

## 5. Cache API

Location:

- `web/src/pages/api/cache.ts`

The cache API is intentionally a disabled/no-op endpoint.

Expected behavior:

- `GET /api/cache` reports cache disabled.
- `DELETE /api/cache` succeeds as a no-op for backward compatibility.
- The endpoint must not expose stale cache keys because there is no active frontend cache.

Expected response shape:

```json
{
  "ok": true,
  "cacheEnabled": false,
  "entries": 0,
  "keys": []
}
```

## 6. Strapi Lifecycle Behavior

Location:

- `src/index.js`

Strapi should not register frontend cache invalidation subscribers while cache is disabled.

Rules:

- Do not add lifecycle hooks that call `DELETE /api/cache` unless active caching is intentionally restored.
- `FRONTEND_URL` may still be used by other features, but it is not required for cache invalidation in the current mode.
- `CACHE_SECRET` is not required for the disabled cache API contract.

## 7. Verification

After any change touching CMS fetches, middleware, sitemap, robots, OG generation, or cache API behavior, verify the no-cache contract.

Check page headers:

```bash
/usr/bin/curl -sSI http://localhost:4321/th/articles | rg -i "cache-control|pragma|expires"
```

Expected:

```text
Cache-Control: no-store, no-cache, must-revalidate, max-age=0, s-maxage=0
Pragma: no-cache
Expires: 0
```

Check cache API state:

```bash
/usr/bin/curl -sS http://localhost:4321/api/cache
```

Expected:

```json
{"ok":true,"cacheEnabled":false,"entries":0,"keys":[]}
```

If a page visibility flag is changed in CMS, verify the frontend reflects the change without manual invalidation.

## 8. Re-Enabling Cache

Caching may be reintroduced only as a deliberate architecture change.

Required work if cache is restored:

- Rebuild `web/src/lib/cache.ts` with real storage, TTLs, and stats.
- Change `web/src/lib/strapi.ts` fetch policy intentionally.
- Replace no-store middleware with a route-aware cache policy.
- Restore secure cache invalidation from Strapi lifecycle hooks.
- Require and document `CACHE_SECRET`.
- Update `/api/cache` authentication, stats, and invalidation behavior.
- Add tests or manual verification for stale content, disabled pages, inactive records, and CMS publish/unpublish behavior.

Until that work is complete, the project rule is: **CMS content should be fetched fresh and frontend responses should not be cached.**
